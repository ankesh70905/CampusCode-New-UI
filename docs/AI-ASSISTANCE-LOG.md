## Important component understanding record

### `LandingPage` (`src/pages/LandingPage.jsx`)

- Purpose: composes the landing page sections and owns which sample event detail dialog is open.
- State: `selectedEvent` is either one event record or `null`.
- Data flow: reads `featuredEvents` from `src/data/events.js`; passes each event to `EventCard`; event selection opens `EventDialog`.
- Interactions: section links scroll to page anchors; sign-in/join actions navigate to honest next-phase notices; reveal observer adds an entrance class when sections enter view.

### `SiteHeader` (`src/components/SiteHeader.jsx`)

- Purpose: sticky responsive navigation and primary account-entry links.
- State: `menuOpen` toggles the compact menu; `activeHash` tracks the visible page section.
- Events: Escape closes an open menu; selecting an anchor or route also closes it. `IntersectionObserver` updates the active link.
- Data flow: navigation items are a local static list; account actions use the router.

### `EventCard` and `EventDialog` (`src/components/`)

- `EventCard` receives an event, its display index, and an `onExplore` callback. Its button passes the event to the parent; it does not register a student.
- `EventDialog` receives the selected event and `onClose`; it shows sample details, closes on Escape or backdrop click, and explicitly says registration is unavailable.
- Event records are static illustrative data from `src/data/events.js`; they do not represent actual event listings.

### `SiteFooter` and `NextPhasePage` (`src/components/`, `src/pages/`)

- `SiteFooter` provides anchor links and router links to the next-phase notices.
- `NextPhasePage` is used for the not-yet-built Student Dashboard and unknown routes. After demo registration it confirms the non-sensitive profile was stored and links to demo login; after demo login it explicitly states no identity was authenticated. It links back home and does not render a dashboard.

### `src/styles.css`

- Defines brand tokens, responsive layout, focus treatment, small CSS transitions/keyframes, and the reduced-motion override.
- Intersection reveal effects and the hero accent are decorative; content remains available without motion, with reduced-motion settings forcing reveals visible and disabling nonessential animation.

### Phase 2 auth components

- `AuthLayout` shares the branded editorial panel, home navigation, form column, demo disclosure, and reciprocal Login/Register link. It accepts page variant, eyebrow, heading, supporting text, and page-specific form content.
- `AuthField` associates labels, values, field hints, and validation errors; password visibility controls are passed through its `trailing` slot.
- `DemoHumanCheck` is a controlled checkbox interaction. It is explicitly not a real CAPTCHA or security boundary.
- `AuthToast` announces feedback through status/alert roles and supports dismissal.
- `LoginPage` owns email/password input state, visibility, remember-preference state, demo human-check, validation errors, simulated submission, forgot-password feedback, and toast/navigation timing. It stores only the optional boolean preference.
- `RegisterPage` owns account form/consent state, password visibility/strength display, local demo profile creation, validation and feedback. It persists only name, email, account type, and timestamp—never a password.
- `loginValidation.js` and `registerValidation.js` are pure functions that return field-keyed error objects. `getPasswordStrength` derives a display label/score; it does not transmit or persist the password.
- `App.jsx` provides route-specific document titles and nests the dashboard routes below `DashboardLayout`.

### Phase 3 dashboard shell and overview

- `DashboardLayout` loads the versioned demo state and keeps a visible error path if reading or writing LocalStorage fails. It provides state, update, reset, and notification callbacks to child routes; navigation and footer disclose the local demo boundary.
- `DashboardOverviewPage` derives overview totals, weekly activity, and streak status from dashboard state. Its learning-session button records one qualifying activity for the local calendar day; refresh does not create activity, and a second same-day check-in is prevented.
- During Phase 3, the overview labeled seeded deadlines, activity, and aggregate counts as illustrative; Events and My Events were then placeholders. Phase 4 later implemented those event experiences.

### Phase 3 dashboard feature routes

- `StudentProfilePage` edits only the non-sensitive dashboard profile and skill list; changes are saved through the shell's `updateDashboard` callback.
- `ProjectsPage` creates, edits, and removes local projects. Saving a project records at most one qualifying project activity per local calendar day; seeded records remain visibly labeled.
- `NotificationsPage` stores read/dismiss state locally and filters example reminders according to `SettingsPage` preferences. No external delivery exists.
- `AchievementsPage` derives example badge states from the event/project records. `CertificatesPage` uses a native dialog for a sample marked not valid; it is a preview, not an issued credential.
- Overview and settings allow bounded weekly-goal changes; the 28-day activity calendar reports only deliberate local activity records.

### Phase 5 growth ecosystem

- `growthLogic.js` contains pure derivations: `getStreakSummary` deduplicates valid local date keys and calculates current/longest runs and milestones; `getMonthlyActivity` builds month cells and day-level action details; `deriveActivityFeed` combines persisted entries with completed registration timelines and sorts newest-first.
- `dashboardState.js` validates and persists schema version 3, migrates v1/v2 data, enforces registered-event references for project links, records one qualifying streak day per local date, and deduplicates achievement and streak-milestone awards. Certificate previews are derived once per completed event registration.
- `ProjectsPage` owns local project forms and validation. `ProjectDetailPage` handles milestone completion, history, status, and linked sample-event navigation. Creating/updating a project, completing a milestone, or submitting to a registered event records local activity; event submission uses its own feed entry.
- `AchievementsPage` derives visible progress from dashboard records and opens `AchievementDetailDialog`; unlock records are local demo achievements, not awards. `CertificatesPage` uses the shared event-derived records and `CertificateDialog`, which is explicitly a non-valid preview.
- `ActivityPage` filters the chronological local/sample feed by action type and links only to matching local project/event routes. The overview's monthly calendar uses activity-log entries for day details, while streak/weekly summaries use only qualifying activity records.
- `StudentProfilePage` stores non-sensitive profile fields and visibility preferences; its public-style preview is not published. `DashboardOverviewPage` combines the derived growth summary with calendar, streaks, and recent activity.
